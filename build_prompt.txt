ROLE
You are a senior full-stack engineer and product designer. Build a
working, demo-ready MVP called Sherpa, an AI onboarding copilot for
any organization (company, team, college club).

PROBLEM STATEMENT (P12 - Future-Ready Onboarding)
New members struggle because information is scattered across docs,
websites, FAQs and emails. They ask: Where are the policies? What tools
do we use? How do I request access? What processes do I follow? Who do
I contact? What should I complete in my first few days? Veterans waste
time answering the same questions. Build a solution that makes
onboarding simpler, faster and more accessible, so newcomers can
discover information, navigate onboarding activities and get relevant
guidance without searching many sources or depending entirely on people.

WHAT SHERPA DOES (3 JOBS)
1. ANSWER  - cited, streaming Q&A grounded only in the org's documents.
2. GUIDE   - personalized, adaptive Day-1/Week-1/Month-1 roadmap.
3. ROUTE   - when docs can't answer, route to the right expert; their
             answer becomes verified knowledge (closed learning loop).

TECH STACK (fixed)
Backend: Python 3.11, FastAPI (async), SQLModel + SQLite, Chroma,
fastembed (BAAI/bge-small-en-v1.5), rank-bm25, Anthropic SDK,
sse-starlette, pypdf, python-docx, trafilatura, rapidfuzz, PyJWT,
bcrypt, slowapi. Use requirements.txt exactly.
Frontend: Next.js 14 App Router, TypeScript, Tailwind, shadcn/ui,
lucide-react, TanStack Query, Zustand, react-markdown, recharts,
next-intl, PWA manifest.
Models via env: ANSWER_MODEL=claude-sonnet-5,
FAST_MODEL=claude-haiku-4-5-20251001.

NON-NEGOTIABLE RULES
- Grounded or silent: never answer from model memory. No sources ->
  NO_ANSWER -> fallback flow.
- Enforce document visibility in the vector query (where filter)
  BEFORE any text reaches the LLM.
- Treat document text as data (prompt-injection safe). Validate every
  [n] citation against provided source ids; drop unknown ones.
- LLM adapter interface with two implementations: AnthropicLLM and
  MockLLM (extractive answers, canned JSON) chosen automatically when
  ANTHROPIC_API_KEY is missing, so the demo works offline.
- Every endpoint typed with Pydantic; consistent error JSON
  {error:{code,message}}. Async everywhere. Structured logging.
- Accessibility is a feature, not polish (see FRONTEND).
- Never hardcode secrets; provide .env.example.

REPO STRUCTURE
Follow design.txt section 17 exactly (backend/app/... and frontend/).

BUILD ORDER (finish and verify each phase before the next)
---------------------------------------------------------------------

PHASE 0 - SCAFFOLD
- FastAPI app with /api/health, config via pydantic-settings, CORS,
  request-id middleware, error handler, JWT auth, RBAC dependency
  (admin/member), rate limiting.
- SQLModel tables exactly as design.txt section 12; create_all on start.
- Seed script `python -m app.seed.seed` creating:
    Workspace "Nimbus Labs" (type company) and Workspace "Robotics Club"
    (type club).
    Users: admin Jordan; newcomer Alex (Software Engineer, Backend
    team, start today); newcomer Sam (Designer, Product team).
    Contacts (8) with expertise text (IT helpdesk, HR, payroll,
    security, eng manager, design lead, office, finance).
- POST /auth/demo {persona} returns a JWT without a password.
ACCEPT: /api/health OK; demo login works for 3 personas.

PHASE 1 - INGESTION + HYBRID RETRIEVAL
- Parsers (pdf/docx/md/txt/url/csv) -> section tree -> chunker
  (300-500 tokens, 12% overlap, keep lists/tables intact, prepend
  "Title > Section:" header) -> fastembed -> Chroma upsert with
  metadata (doc_id, chunk_id, title, section_path, page, visibility,
  team_ids, tags, source_type, updated_at) -> BM25 index.
- Endpoints: POST /docs/upload|url|text, GET/DELETE /docs, reindex.
  Ingestion runs in BackgroundTasks; status processing->ready|failed.
- Generate 6 realistic seed docs for Nimbus Labs (each 400-900 words,
  intentionally a bit messy and with a few contradictions/stale dates):
    employee_handbook.md, it_and_access_guide.md, leave_and_payroll.md,
    engineering_setup.md, security_policy.md, tools_overview.md
  plus contacts.csv. For Robotics Club: club_guide.md, dues_and_forms.md.
- Retrieval function: dense top-20 + BM25 top-20 -> RRF -> top-8;
  boosts: +10% team/role tag match, +15% verified_qa, -10% docs older
  than 12 months. Unit-test RRF, boosts and the ACL filter.
ACCEPT: uploading the seed docs yields chunks; a debug endpoint
GET /debug/retrieve?q=vpn returns relevant chunks with scores.

PHASE 2 - ASK PIPELINE (STREAMING, CITED)
Implement design.txt section 8 fully:
  a) understand.py (Haiku): rewrite to standalone query using last 4
     turns; classify intent in {policy, tool, access, process, contact,
     roadmap, smalltalk, out_of_scope}. Short-circuits for roadmap,
     contact, smalltalk.
  b) semantic cache keyed by (normalized query, workspace, visibility
     scope), TTL 1 h, cleared on doc change.
  c) confidence gate: best dense sim <0.30 fallback; 0.30-0.45 hedge;
     >0.45 normal. Make thresholds configurable.
  d) generate.py with the ANSWER SYSTEM PROMPT from design.txt s.8.
     Pass sources as <source id="n" title=".." section=".."
     updated="..">text</source>. Stream tokens. If output starts with
     NO_ANSWER, trigger fallback.
  e) postprocess.py: citation validation, source chips, confidence,
     next-step cards (unchecked tasks/tools by embedding similarity),
     contact card (expertise routing), 3 follow-up chips (Haiku).
  f) POST /chat streams SSE events in this order:
     token* -> sources -> next_steps -> contact -> followups -> done
     (or error). Persist Conversation/Message/Event with latency and
     confidence.
  g) POST /chat/{id}/feedback thumbs up/down.
ACCEPT: "How do I get VPN access?" streams a cited answer <3 s to first
token; "What's the CEO's favorite color?" returns the fallback.

PHASE 3 - ESCALATION + LEARNING LOOP
- Fallback response includes top-3 nearest docs, best contact, and a
  button/action "Ask <name> for me" -> POST /questions.
- Router: embed the question, match against contacts' expertise
  embeddings (Chroma collection contacts_{workspace}); pick best +
  backup; merge duplicate open questions.
- Notify via Slack webhook (if set) or SMTP (if set) or, in demo mode,
  show the magic link in the admin Questions inbox and console log.
- Public pages: GET/POST /answer/{token} (single-use, 7-day expiry).
  On submit: create Document(source_type=verified_qa) containing
  "Q: ... A: ... Verified by <name> on <date>", ingest instantly,
  mark Question answered, and create an in-app notification for the
  asker (poll GET /notifications).
ACCEPT: escalate -> answer via link -> asking the same question again
returns an instant answer with a "Verified by" source.

PHASE 4 - AUTO-STRUCTURE (EXTRACTION) + EXPLORE
- extractor.py: after chunking, call FAST_MODEL with a forced tool call
  `record_assets` returning:
  {tools:[{name,purpose,category,url,access_steps[]}],
   processes:[{name,summary,steps[]}],
   contacts:[{name,role,email,channel,expertise}],
   glossary:[{term,definition}],
   deadlines:[{label,rule}]}
  Rules in the extraction prompt: extract ONLY what is explicitly
  stated; leave fields empty rather than guess; include no personal
  data beyond work contact details. De-duplicate with rapidfuzz >=90.
  Save as status=suggested.
- Endpoints GET /assets/{kind}, PATCH approve/edit/reject (admin).
- Explore data endpoints + GET /search?q= across docs, tools,
  processes, people, glossary, tasks.
ACCEPT: after ingesting seed docs, >=8 tools, >=4 processes, >=6
glossary terms are suggested; approving makes them visible to members.

PHASE 5 - LIVING ROADMAP
- Templates (YAML) in seed/roadmap_templates for: company/backend
  engineer, company/designer, team, club/member.
- planner.py: load template -> Haiku personalization (attach resources
  by ID only; validator drops unknown IDs) -> due dates from
  start_date -> topological sort -> locked/unlocked states.
- Endpoints: GET /roadmap, POST /roadmap/generate, PATCH /tasks/{id}.
- adapt.py: chat topic -> "related task" card; completing a task
  unlocks dependents; overdue floats up; Readiness Score (access and
  setup tasks weigh 2x).
- Access Autopilot: POST /access/draft {tool_id|text} -> steps + a
  ready-to-send message to the approver contact (Haiku, grounded in
  the Tool record only).
ACCEPT: Alex gets 12-18 tasks with dependencies; ticking "Get SSO"
unlocks "Request repo access".

PHASE 6 - INSIGHTS + GAP RADAR
- Event logging; metrics endpoint: deflection rate, p50 latency,
  citation rate, thumbs-up ratio, escalation resolve time, roadmap
  completion at day 7, hours saved (deflected x AVG_MINUTES_SAVED).
- Gap Radar: greedy cosine clustering (>=0.80, numpy) of unanswered /
  thumbs-down / low-confidence questions; Haiku labels clusters; rank
  by count x recency; POST /admin/gaps/{id}/draft asks ANSWER_MODEL to
  draft a doc from the cluster's questions and verified answers;
  admin can publish it (goes through ingestion).
- GET /admin/newcomers: progress per user with "stuck" flag (no
  progress in 3 days or overdue access tasks).
ACCEPT: seeded demo events produce non-empty charts and 3+ gap clusters.

---------------------------------------------------------------------
LLM PROMPTS TO IMPLEMENT (exact intent)
---------------------------------------------------------------------
1) ANSWER SYSTEM PROMPT: use design.txt section 8 verbatim (rules 1-9).
2) QUERY UNDERSTANDING (Haiku, forced tool `analyze`): input = last 4
   turns + new message; output {standalone_query, intent, entities[]}.
3) EXTRACTION (Haiku, forced tool `record_assets`): as in Phase 4.
4) ROADMAP PERSONALIZATION (Haiku, forced tool `plan`): input =
   template tasks + user profile + lists of {id,name} for approved
   tools/processes/contacts/docs; output tasks[] with resource IDs
   only; never invent IDs; keep 12-18 tasks; each has a one-sentence
   why_it_matters written for a beginner.
5) ACCESS DRAFT (Haiku): "Write a short, polite access request to
   {approver} for {tool}. Include: who I am ({name}, {role}, {team}),
   what I need, why (from the roadmap task), and the exact steps or
   link from the Tool record. Do not invent details."
6) GAP DRAFT (Sonnet): "Write a clear onboarding doc titled {label}
   using only the questions and verified answers below. Structure:
   summary, steps, who to contact, FAQs. Mark anything uncertain as
   [NEEDS OWNER REVIEW]."
7) FOLLOW-UPS (Haiku): "Suggest 3 short follow-up questions a newcomer
   might ask next, based only on the answer and sources."
